# 자체 제작 마을·도로 높이맵 비교 감사

측정·감사: 2026-10-12. 구현은 Claude Code의 Opus 작업 1개와 Sonnet 작업 2개에 맡겼고, Codex는 검토, 수정 요청, 독립 실행과 결과 검증을 담당했다. CLI의 모델 별칭은 실행 기록에서 `claude-opus-5`, `claude-sonnet-5`로 확인했다. 기존 코덱은 변경하지 않았다.

## 데이터와 범위

오루알사의 마을과 연결 도로라는 구조를 참고한 **독창적인 합성 uint16 높이맵**이다. 실제 게임 맵, ROM, 메시, 텍스처를 사용하지 않았다. 계단식 평원·절벽, 광장과 건물 부지, 하천, 다리·여울, 연결 도로, 시드 기반 세부 기복을 포함한다. 건물 부지는 건물 메시가 아니며, 높이맵은 교량 아래와 위의 공간을 동시에 표현하지 못한다. 안내 이미지의 선과 표식은 생성기 메타데이터를 표시한 것이다.

기본 입력은 1024×1024, 2,097,152바이트, seed=20261012이다. 높이는 5745~7644, 서로 다른 값은 1870개이며 가로 이웃 값의 약 47.6%가 같다. 부드럽고 정수로 만든 합성 입력이라는 특성을 고려해야 한다. 같은 환경에서 입력 SHA-256을 재생성해 확인했다. 서로 다른 NumPy 빌드·CPU에서 부동소수점 생성 결과까지 동일하다고 보장하지 않는다.

## 측정과 독립 검사

- Zstd, LZ4, 행 차분+Zstd 각각에 대해 청크 크기 64/128/256/512를 비교했다.
- 기본 맵, 다른 시드의 1024 맵, 경계 처리를 위한 1025 맵: 총 36개 설정, 설정별 30회, 각 측정 경로 사전 워밍업 1회.
- 전체 압축/복원, 모든 청크 압축/재구성, 한 청크 조회·복원, 전체 복원 후 동일 영역 복사를 따로 측정했다. 각 쌍의 실행 순서는 반복마다 교대했다.
- 요청 청크는 시드 기반 순열을 순환하며 코덱마다 동일한 일정을 사용한다. 청크 쪽은 직렬화 인덱스의 O(1) 조회와 바이트 슬라이스를 포함한다. 전체 쪽도 독립 배열로 영역을 복사한다.
- 측정 안에는 코덱의 체크섬 검사가 포함된다. 입력과의 정확 일치·인코딩 결정성 검사는 시간 구간 밖에서 수행한다.
- 저장 비용은 실제 직렬화 인덱스 `24 + 32*N` 바이트와 각 청크의 60바이트 코덱 헤더 및 압축 페이로드를 모두 포함한다. 단일 컨테이너 대비 **추가** 관리 비용은 `24 + 32*N + 60*N - 60`바이트다.
- Codex는 세 입력 해시를 재생성하고, 36개 설정의 정확 복원 플래그·용량 합계·인덱스 크기·요청 개수와 모든 시간 표본 개수를 확인했다. 저장된 표본으로 중앙값과 p95도 재계산해 반올림 오차 범위에서 일치함을 확인했다.

환경: macOS 26.6.2 arm64, Python 3.13.9, NumPy 2.5.4, zstandard 0.25.0, lz4 4.4.5. 일반 데스크톱의 단일 실행으로 CPU 격리나 시스템 전체 유휴 상태를 보장하지 않는다. 원시 표본과 환경은 각 JSON에 있다.

## 기본 맵 결과

차분+Zstd의 단일 전체 컨테이너는 **367.03 KiB**다. 직접 Zstd의 486.47 KiB보다 24.55% 작지만, 복원은 직접 Zstd가 더 빠르다. 아래 시간은 중앙값이며 p95는 원시 JSON에서 확인할 수 있다.

| 청크 한 변 | 인덱스 포함 총 KiB | 전체 컨테이너 대비 | 모든 청크 복원 ms | 한 청크 조회·복원 ms | 전체 복원 후 같은 영역 복사 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 | 418.71 | +14.08% | 4.671 | 0.048 | 3.994 |
| 128 | 378.35 | +3.08% | 4.061 | 0.119 | 3.949 |
| 256 | 367.47 | +0.12% | 3.927 | 0.248 | 3.907 |
| 512 | 366.24 | −0.22% | 4.073 | 1.008 | 3.910 |

256 설정에서 단일 전체 복원 중앙값은 3.934ms, 모든 청크 재구성은 3.927ms다. 이 작은 차이를 전체 복원 속도 개선으로 판정하지 않는다. 한 청크 복원의 p95는 0.288ms다. 다른 시드에서도 256 청크의 용량 증가 +0.38%, 한 청크 복원 중앙값 0.254ms로 비슷한 절충을 확인했다.

청크 크기가 다르면 요청하는 영역 면적도 달라진다. 표의 부분 복원 시간끼리 동일한 작업량으로 비교해서는 안 된다. 각 행에서 동일 영역을 반환하는 두 방식만 직접 비교할 수 있다. 작은 청크일수록 무조건 최적이라고 결론 내리지 않는다.

### 경계 맵의 요청 분포

1025×1025 맵은 경계 청크와 정확 재구성 검증을 위한 입력이다. 이번 요청 방식은 픽셀이 아닌 **청크를 균등하게** 고른다. 512 설정에서는 30회 중 17회가 폭이나 높이가 1인 경계 청크여서 부분 복원 중앙값이 0.050ms로 내려간다. 이는 더 작은 작업량 때문이며 기본 맵보다 빠르다는 근거로 사용할 수 없다. 실제 스트리밍 실험에서는 고정 면적 요청 또는 좌표 기반 접근 분포와 여러 청크에 걸친 요청을 별도로 측정해야 한다.

## 감사에서 보완한 사항과 한계

첫 청크 구현의 고정된 단일 요청·고정 측정 순서를 반려하고 여러 청크 요청과 교대 순서로 수정하도록 했다. 미리 추출한 청크 바이트만 복원하던 경로에는 실제 인덱스 조회·슬라이스를 넣었으며, 전체 복원 쪽의 crop도 소유 배열로 맞췄다. 최소 반복 횟수와 충돌하는 신규 테스트도 수정하도록 했다. 이 수정 이전의 짧은 연동 실행은 최종 결과로 사용하지 않았다.

인덱스는 내부에서 생성한 바이트만 읽는 실험용이며, 악의적 입력의 범위·겹침·누락·체크섬을 검증하는 공개 저장 포맷이 아니다. 디스크 I/O, 엔진 객체·GPU·충돌 준비, 실제 게임 에셋, RSS/네이티브 피크 메모리, 사전 Zstd, 연속 이동과 캐시 재사용은 측정하지 않았다.

이 범위에서는 **256 청크를 다음 부분 읽기 실험의 출발점**으로 삼을 수 있다. 차분 방식은 저장 비용에, 직접 Zstd/LZ4는 복원 지연에 이점이 있어 코덱 선택은 런타임 예산과 접근 패턴을 측정한 뒤 결정해야 한다.

## 재현과 산출물

```sh
uv sync
uv run python -m unittest discover -s tests
uv run python scripts/compare_town.py --size 1024 --seed 20261012 --repeats 30 --output benchmarks/my-town.json --preview-dir data/terrain-local/my-town
uv run python scripts/compare_town.py --size 1024 --seed 20261013 --repeats 30 --output benchmarks/my-town-seed2.json
uv run python scripts/compare_town.py --size 1025 --seed 20261012 --repeats 30 --output benchmarks/my-town-edge.json
```

출력은 새 경로를 사용한다. 기본 입력 NPY와 원본 SVG는 로컬 `data/terrain-local/town-preview/`에 두었고 Git 제외 대상이다. PNG 안내 이미지는 `benchmarks/town-layout.png`에 있다.

- 기본 결과: `town-1024-v1.json`
- 다른 시드: `town-1024-seed2-v1.json`
- 경계 입력: `town-1025-edge-v1.json`
- 실행 계약·포맷 설명: `../docs/town-benchmark-method.md`
- 소스·결과 해시와 최종 테스트 상태: `town-audit-evidence.json`
