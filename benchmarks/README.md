# 초기 합성 데이터 벤치마크

측정일: 2026.10.12. 모든 입력은 합성 데이터이며 실제 제작된 게임 월드가 아니다.

- 배열: 256×256 little-endian uint16, 원본 값 바이트열 131,072바이트.
- 비교: Zstd level 3, LZ4 프레임 기본값, 행별 왼쪽 차분 후 Zstd level 3.
- 방식별 워밍업 1회와 측정 30회. 모든 반복에서 shape·dtype·원본 바이트 일치 확인.
- 크기는 60바이트 헤더를 포함한 전체 컨테이너 크기다.
- 시간은 메모리 내 encode/decode 전체 호출이며 체크섬 비용을 포함한다.
- 환경: Windows, Python 3.10.6, NumPy 2.2.6, zstandard 0.25.0, lz4 4.4.5.
- 원본 결과: [synthetic-256.json](synthetic-256.json). 입력 해시·시드·상세 환경·설정 포함.

| 합성 입력 | 직접 Zstd 크기 | 차분+Zstd 크기 | 직접 Zstd 복원 p95 | 차분+Zstd 복원 p95 |
| --- | ---: | ---: | ---: | ---: |
| 상수 | 82 B | 87 B | 0.2236 ms | 0.2990 ms |
| 평면 | 9,164 B | 1,004 B | 0.2337 ms | 0.3345 ms |
| 부드러운 지형 | 131,144 B | 24,691 B | 0.2329 ms | 0.3981 ms |
| 난수 | 131,144 B | 131,144 B | 0.2302 ms | 0.3089 ms |

부드러운 합성 지형에서 차분+Zstd는 직접 Zstd보다 약 81% 작고, 복원 p95는 약 71%
느렸다. 평면에서도 용량 이득과 복원 시간 증가가 함께 나타났다. 상수는 직접 Zstd가
더 작았고 난수는 용량 이득이 없었다. 모든 데이터에 차분을 강제할 근거는 없다.

측정 명령:

```powershell
uv run python -m horizon benchmark --size 256 --repeats 30 --output benchmarks/new-run.json
```

출력 파일이 이미 있으면 덮어쓰지 않는다. 타이밍은 현재 장치의 단일 실행 결과이며
반복 측정과 장치 간 비교가 필요하다. 실측 메모리, 디스크 I/O, 엔진 객체 구성,
GPU 업로드, 충돌 준비, 사전 Zstd 기준선과 실제 수제 높이맵은 아직 평가하지 않았다.
기본 예측기는 고정된 행별 차분이며 자동 규칙 추론도 아직 구현하지 않았다.

## 복원 개선과 실제 지형 (2026-10-12, Windows DEM)

위 표는 초기 버전의 역사적 기록이다. 새 비교는 보존한 이전 코덱과 현재 코덱을
같은 실행에서 교대로 측정했다. 공개 Skadi DEM 두 타일(각 3601×3601), 중앙 크롭,
합성 4종을 방식별 워밍업 5회·측정 50회 실행했다. 체크섬 검사는 시간에 포함된다.

| 전체 타일의 차분+Zstd | 이전 중앙값 | 현재 중앙값 | 이전 p95 | 현재 p95 |
| --- | ---: | ---: | ---: | ---: |
| 한국 N37E127 | 98.8238 ms | 85.5461 ms | 106.8574 ms | 97.5503 ms |
| 알프스 N46E007 | 100.2365 ms | 86.4612 ms | 109.0717 ms | 94.9466 ms |

전체 타일의 중앙값은 약 13~14%, p95는 약 9~13% 줄었다. 1024 크롭의 중앙값은
약 11% 줄었고 256 합성 맵은 사실상 이전 수준이다. 전체 타일의 현재 직접 Zstd
중앙값은 각각 81.9383ms, 81.8254ms로 차분+Zstd보다 빠르다. 대신 차분 컨테이너는
직접 Zstd보다 각각 33.50%, 40.77% 작다. 작은 맵의 차분 복원 비용은 남아 있다.

일반화하지 않는다. 실제 수제 게임 높이맵과 사전 Zstd는 여전히 미검증이다.

## 디스크 읽기+복원 비교 (2026-10-12, Windows DEM)

같은 공개 전체 지형 두 타일을 현재 직접 Zstd와 차분+Zstd로 저장해 비교했다.
매번 파일을 다시 열어 읽고 닫은 뒤 복원하며, 체크섬까지 전체 시간에 포함했다.
파일 캐시 사용 조건은 직전에 전체 파일을 읽어 준비했고, 캐시 우회 조건은 Windows
`FILE_FLAG_NO_BUFFERING`을 사용했다. SSD·컨트롤러 캐시와 메타데이터는 비우지 않았다.

| 전체 파일 읽기+복원 | 직접 Zstd 중앙값 / p95 | 차분+Zstd 중앙값 / p95 |
| --- | ---: | ---: |
| 한국, 캐시 사용 | 82.8357 / 98.7448 ms | 86.5765 / 101.8089 ms |
| 알프스, 캐시 사용 | 84.5971 / 90.8549 ms | 86.9619 / 99.5722 ms |
| 한국, OS 캐시 우회 | 92.7157 / 110.2883 ms | 92.8759 / 105.6630 ms |
| 알프스, OS 캐시 우회 | 93.5403 / 106.7221 ms | 94.7094 / 108.2406 ms |

조건·방식별 워밍업 2회·측정 50회, 총 400개 측정 표본이다. 방식 순서를 반복마다
바꾸고 캐시 조건 순서도 교대했다. 모든 복원 결과와 측정 전후 파일 해시를 검증했다.
중앙값 기준 차분+Zstd는 캐시 사용 시 2.8~4.5% 느렸고, 캐시 우회 시 0.2~1.2%
느렸다. 캐시 우회 결과는 사실상 동률에 가까우며, p95 방향도 두 지형에서 달랐다.
단일 실행의 작은 차이를 확실한 속도 우위로 해석하지 않는다. 용량은 이전과 동일하게
직접 Zstd보다 약 34~41% 작았다.

- [최종 결과와 원시 표본](disk-load-real-v2.json)
- [감사 보고서와 재현 명령](disk-load-audit.md)
- [실제 Windows 호출·정렬·오류 정리 검증](disk-load-native-evidence.json)

초기 읽기 구현은 실제 파일 대신 65MiB 상한 크기를 요청해 불필요한 할당 비용이
붙었다. 이 결과는 반려하고 실제 파일 크기만 읽도록 수정했다.
`rejected-disk-*` 결과는 그 감사 증거이며 최종 성능 비교에 사용하지 않는다.

측정 환경: 단일 Windows 장치, Python 3.10.6, NumPy 2.2.6, zstandard 0.25.0, lz4 4.4.5.
이 시점 자동 테스트는 130개 중 127개 통과·3개 건너뛰기였다(Windows 캐시 우회 검사는
실제 실행, 건너뛴 항목은 심볼릭 링크 권한 검사 2개와 비-Windows 전용 검사 1개).

## 합성 마을·도로 맵: 전체 대 청크 압축 (2026-10-12, macOS)

오루알사의 마을·연결 도로 구조를 참고한 **독창적인 합성 uint16 높이맵**이다.
실제 게임 맵, ROM, 메시, 텍스처는 사용하지 않았다. 계단식 평원·절벽, 광장과
건물 부지, 하천, 다리·여울, 연결 도로, 시드 기반 세부 기복을 포함한다. 기본
입력은 1024×1024(2,097,152바이트, seed=20261012). Zstd/LZ4/차분+Zstd ×
청크 변 64/128/256/512를 기본 맵·다른 시드 맵·1025 경계 맵에 걸쳐 총 36개
설정, 설정별 30회 측정했다.

| 청크 한 변 | 인덱스 포함 총 KiB | 전체 컨테이너 대비 | 모든 청크 복원 ms | 한 청크 조회·복원 ms | 전체 복원 후 같은 영역 복사 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 | 418.71 | +14.08% | 4.671 | 0.048 | 3.994 |
| 128 | 378.35 | +3.08% | 4.061 | 0.119 | 3.949 |
| 256 | 367.47 | +0.12% | 3.927 | 0.248 | 3.907 |
| 512 | 366.24 | −0.22% | 4.073 | 1.008 | 3.910 |

차분+Zstd 단일 전체 컨테이너는 367.03 KiB로 직접 Zstd(486.47 KiB)보다 24.55%
작지만 복원은 직접 Zstd가 더 빠르다. 1025 경계 맵은 청크를 균등하게 고르므로
512 설정의 부분 복원 중앙값(0.050ms)은 작은 경계 청크 때문이며 속도 우위 근거로
쓰지 않는다. 환경: macOS 26.6.2 arm64, Python 3.13.9, NumPy 2.5.4, zstandard
0.25.0, lz4 4.4.5.

디스크 I/O, 엔진·GPU·충돌 준비, RSS/네이티브 피크 메모리, 사전 Zstd, 연속 이동과
캐시 재사용은 이 비교에서 측정하지 않았다. 256 청크를 다음 실제 디스크 실험의

## 256청크 실제 디스크 저장: 전체 대 부분 로딩 (2026-10-12, macOS)

같은 합성 마을·도로 맵 두 개(시드 20261012·20261013)를 256×256 청크(맵당
16개)로 단일 컨테이너와 청크 컨테이너 두 가지 실제 파일로 저장했다. 3코덱 ×
2캐시 조건(`warm_buffered`, `macos_nocache`) × 2작업(전체/부분) × 2저장 방식을
워밍업 2회 후 50회 실행, 두 맵 합계 2,400회 로딩 표본을 측정했다.

차분+Zstd, 기본 맵, 시간은 **중앙값 / p95, ms**(파일 열기~복원 완료):

| 작업 | 캐시 준비 일반 읽기 | F_NOCACHE 요청 |
| --- | ---: | ---: |
| 단일 파일 전체 로딩 | 4.184 / 4.354 | 4.225 / 4.656 |
| 청크 파일 전체 로딩 | 4.239 / 4.684 | 4.271 / 5.044 |
| 단일 파일 전체 읽기·복원 후 영역 복사 | 4.205 / 4.488 | 4.243 / 4.489 |
| 선택한 청크만 읽기·복원 | 0.286 / 0.342 | 0.273 / 0.359 |

캐시 준비 조건에서 정렬된 단일 청크의 부분 로딩은 전체 로딩 대비 **약 14.7배**
빨랐고, 전체 로딩은 청크 방식이 오히려 약 1.3% 느려 이득이 없었다. 부분 청크의
애플리케이션 읽기량은 단일 방식(375,841바이트) 대비 중앙값 기준 약 93.7% 적다.
Zstd/LZ4/차분+Zstd 세 코덱 모두 같은 경향을 보였고, 다른 시드에서도
약 13.6~14.7배로 재현됐다.

**F_NOCACHE 요청은 이미 존재하는 캐시 페이지를 제거했다는 검증된 증거가 아니며,
SSD·컨트롤러 캐시까지 비운 물리적 콜드 읽기가 아니다.** HCIX는 여전히 실험용
포맷으로, 전체 인덱스 구조와 읽은 청크의 무결성만 검사하며 읽지 않은 청크의
손상을 검출한다고 주장하지 않는다. 범위는 하이트맵 전용이며 엔진·GPU·충돌
준비, 콜드 부팅, 다른 하드웨어는 검증하지 않았다. 현재 부분 API는 격자에 맞는
청크 하나만 반환하며, 임의 ROI와 연속 이동은 다음 섹션에서 다룬다.

이 시점 전체 테스트: 244개 중 239개 통과·5개 건너뛰기(Windows 전용 4개, 비-Darwin
전용 1개). 환경: macOS 26.6.2 arm64, Python 3.13.9, NumPy 2.5.4.

## 임의 경계 교차 ROI와 연속 이동 120단계 (2026-10-12, macOS)

`horizon/town_region.py`의 `load_region(path, region, mode)`는 청크 경계와
무관한 임의 사각형 ROI를 겹치는 청크만 읽어 정확히 합성한다. 같은 합성 맵
두 시드, 3코덱, 2 I/O 모드로 걷기·경계 왕복·순간이동 세 경로를 120단계 × 3회
반복으로 실행해 총 25,920회 로딩을 측정했다. 응용 프로그램 캐시와 미리
가져오기는 양쪽 비교군 모두 두지 않았다.

시드 20261012, `warm_buffered`, 단위 ms(전체/부분은 요청당 중앙값, 부분은 p95·최대 포함):

| 코덱 | 이동 | 전체 | 부분 | 부분 p95 | 부분 최대 | 속도 비율 | 읽기량 감소 |
|---|---|---:|---:|---:|---:|---:|---:|
| zstd | 걷기 | 2.502 | 0.608 | 0.758 | 2.958 | 4.11× | 81.4% |
| zstd | 경계 왕복 | 2.503 | 0.670 | 0.757 | 0.893 | 3.74× | 75.3% |
| zstd | 순간이동 | 2.499 | 0.614 | 0.771 | 0.940 | 4.07× | 81.6% |
| lz4 | 걷기 | 1.756 | 0.441 | 0.570 | 0.876 | 3.98× | 81.6% |
| lz4 | 경계 왕복 | 1.731 | 0.481 | 0.643 | 1.137 | 3.60× | 74.4% |
| lz4 | 순간이동 | 1.737 | 0.453 | 0.718 | 1.815 | 3.83× | 81.5% |
| delta_zstd | 걷기 | 4.470 | 1.051 | 1.239 | 1.586 | 4.25× | 81.3% |
| delta_zstd | 경계 왕복 | 4.561 | 1.177 | 1.583 | 2.855 | 3.88× | 74.6% |
| delta_zstd | 순간이동 | 4.750 | 1.115 | 1.597 | 5.181 | 4.26× | 81.4% |

경계를 넘어 매번 네 청크를 읽는 경계 왕복(차분+Zstd 1.177ms)은 이전의 정렬된
단일 청크 조회(약 0.286ms, 약 14.7배 개선)보다 이득이 작다. 이번 측정은 약
3.88~4.26배이며, 실행 시점이 달라 이전 결과와 엄밀히 직접 비교하지 않는다.
두 시드의 F_NOCACHE 요청 모드도 차분+Zstd에서 약 3.88~4.54배였다.

**이 단계까지는 애플리케이션 캐시나 미리 가져오기를 두지 않았다.** 이동 간
겹치는 청크를 재사용하는 **제한된(bounded) 캐시 대 전체 맵 상주(resident)
비교**는 다음 섹션에서 초기 로딩·최대 메모리·캐시 미스 지연과 함께 측정했다.
`macos_nocache`의 F_NOCACHE 요청은 캐시를 비웠다고 검증한 콜드
하드웨어 읽기가 아니다. HCIX는 여전히 실험용 포맷이며 범위는 하이트맵 전용이다.

이 시점 전체 자동 테스트 300개: 295개 통과, 환경별 5개 건너뛰기(Windows 전용 4개,
비-Darwin 전용 1개). 별도로 513×769 직사각형 맵에서 무작위 ROI 450개를 독립
검산했다. 환경: macOS 26.6.2 arm64, Python 3.13.9, NumPy 2.5.4.

- [기본 시드 결과](town-movement-1024-v1.json) · [다른 시드 결과](town-movement-1024-seed2-v1.json)
- [감사 보고서](town-movement-audit.md) · [감사 증거](town-movement-audit-evidence.json) · [독립 감사 스크립트](audit_town_movement.py)
- [실행 계약·포맷 설명](../docs/town-movement-method.md)

```sh
uv run python scripts/compare_town_movement.py --size 1024 --seed 20261012 --steps 120 --repeats 3 --output benchmarks/my-town-movement.json --containers-dir data/terrain-local/my-town-movement
```

로컬 컨테이너를 읽고 감사 evidence JSON을 다시 쓴다.

## 제한된 청크 캐시 대 전체 맵 상주 (2026-10-13, macOS)

`horizon/town_cache.py`는 두 가지 상태 유지 로더를 제공한다. `ChunkRegionCache`는
복원된 청크를 용량 제한 LRU로 보관해 이동 중 겹치는 청크를 다시 읽지 않고,
`WholeMapResident`는 시작할 때 전체 파일을 한 번 읽어 복원한 뒤 이후 요청을
메모리 복사로만 처리한다. `scripts/compare_town_cache.py`는 이 둘과 캐시 없는
`load_region()`을 **같은 좌표 위에서** 비교한다. 새 맵도 새 경로도 만들지 않고,
기존 이동 리포트(`--schedule`)의 기록된 좌표를 그대로 재생하며, 기록된
`(size, seed)`로 맵을 다시 만들어 해시를 대조하고 기록된 `source_files_sha256`의
모든 파일이 바이트까지 동일한지 확인한 뒤에야 실행한다.

비교군은 `stateless`(캐시 없음), `lru4`, `lru8`, `whole_resident` 네 개다. 두 시드
(20261012·20261013), 3코덱, 2 I/O 모드(`warm_buffered`, `macos_nocache`),
세 경로(걷기·경계 왕복·순간이동)를 기록된 256청크·256×256 시야로 120단계 × 3회
반복 재생해 **두 시드 합계 51,840회 로딩**을 측정했다. 요청마다 비교군 실행 순서를
회전하고 반복마다 세션을 새로 만들었으며, 반환 배열의 타입·shape·dtype·바이트
일치는 타이머 밖에서 매번 검사했다. 메모리는 시간과 분리해, 표본마다 새 Python
프로세스를 띄우는 `scripts/measure_town_cache_memory.py`로 **216회 독립 측정**했다.

시드 20261012, delta+Zstd, `warm_buffered`, 요청당 **중앙값 / p95, ms**(셀당 360개 요청):

| 방식 | 걷기 | 경계 왕복 | 순간이동 | 보관 배열 상한 |
|---|---:|---:|---:|---:|
| stateless | 0.9010 / 1.0263 | 0.9749 / 1.0761 | 0.9243 / 1.0690 | 0.00 MiB |
| lru4 | 0.0080 / 0.2991 | 0.4726 / 0.5334 | 0.4958 / 0.9865 | 0.50 MiB |
| lru8 | 0.0077 / 0.2663 | 0.0082 / 0.0136 | 0.2645 / 0.8500 | 1.00 MiB |
| whole_resident | 0.0037 / 0.0097 | 0.0033 / 0.0079 | 0.0075 / 0.0117 | 2.00 MiB |

| 이동 | 4청크 적중률 | 8청크 적중률 | 8청크 실제 보관 피크 |
|---|---:|---:|---:|
| 걷기 | 95.57% | 95.84% | 1.00 MiB |
| 경계 왕복 | 49.58% | 98.75% | 0.75 MiB |
| 순간이동 | 21.41% | 52.39% | 1.00 MiB |

적중률에는 비어 있던 캐시의 첫 요청도 포함된다. 경계 왕복은 필요한 여섯 청크가
8청크 캐시에 모두 들어가면 계속 적중하지만, 4청크 용량은 여섯 개를 담지 못해
계속 교체한다.

준비 포함 120단계 로더 시간 합계의 중앙값(반복별 합계를 구한 뒤 중앙값, ms)과
첫 시야까지의 중앙값(ms):

| 이동 | stateless | lru4 | lru8 | whole_resident |
|---|---:|---:|---:|---:|
| 걷기 | 87.431 | 4.866 | 4.576 | 4.667 |
| 경계 왕복 | 118.401 | 58.397 | 2.582 | 4.664 |
| 순간이동 | 89.385 | 68.246 | 41.418 | 4.992 |
| 첫 시야(걷기/경계/순간) | 0.937 / 1.007 / 0.525 | 0.961 / 1.025 / 0.509 | 0.942 / 1.010 / 0.507 | 4.079 / 4.205 / 4.081 |

**이번 측정에서 전체 맵 상주의 요청당 중앙값이 가장 짧았고, 순간이동의 초기화
포함 합계도 가장 작았다.** 대신 첫 시야 비용을 약 4.08~4.21ms 한 번에 치른다(LRU는 약
0.51~1.03ms). 8청크 캐시는 경계 왕복에서 합계 2.582ms로 전체 상주(4.664ms)보다
좋았고 걷기는 4.576ms 대 4.667ms로 **사실상 비슷**하지만, 순간이동에서는
41.418ms 대 4.992ms로 크게 뒤집힌다. **어느 방식도 보편적 우위가 아니다.**
작업 경로와 허용 메모리가 선택을 결정하며, 이 작은 2MiB 맵 하나에 대한 결과를
메모리보다 큰 맵이나 여러 맵 동시 상주로 일반화하지 않는다.

4청크 캐시의 순간이동 최대 요청은 **31.677208ms**였다(같은 셀 p95 0.9865ms).
두 번째 시드에서는 8청크 순간이동 최대가 29.5486ms(p95 0.9800ms)로 같은 성격의
단발 이상치가 나타났다. **원인은 귀속하지 않았고 표본도 제거하지 않았다.**
낮은 중앙값은 게임 프레임 지연 보장을 뜻하지 않는다. 두 번째 시드의 전체 방향은
동일했다. 8청크 요청 중앙값은 걷기 0.0079·경계 왕복 0.0110·순간이동 0.4639ms,
전체 상주는 0.0040·0.0073·0.0100ms였고, 합계는 경계 왕복 2.979ms 대 5.521ms,
순간이동 46.813ms 대 5.798ms였다. 두 시드·세 코덱·F_NOCACHE 요청 모드의 세부
수치는 원시 리포트에 있다.

### 메모리: 세 가지를 구분해서 적는다

시드 20261012, delta+Zstd, 걷기, 독립 프로세스 3회 중앙값, 단위 MiB:

| 방식 | 보관 복원 배열 피크 | tracemalloc 준비 피크 | tracemalloc 이동 피크 | RSS HWM 기준 | RSS HWM 전체 |
|---|---:|---:|---:|---:|---:|
| stateless | 0.000 | 0.000 | 0.629 | 35.781 | 38.375 |
| lru4 | 0.500 | 0.007 | 0.942 | 36.234 | 37.469 |
| lru8 | 1.000 | 0.007 | 1.443 | 36.062 | 38.516 |
| whole_resident | 2.000 | 5.578 | 2.135 | 35.750 | 40.875 |

보관 복원 배열 크기는 측정 잡음이 없는 **정확한 값**이다. 4청크는 0.5MiB,
8청크는 1.0MiB가 구조적 상한이고 전체 상주는 2.0MiB이며, 경계 왕복의 8청크는
필요한 청크가 여섯 개여서 **실제 보관 피크가 0.75MiB**였다. 호출자에게 돌려주는
256×256 출력 배열은 네 방식 모두 0.125MiB여서 이 열에서 제외했고, 인덱스·Python
객체·압축 입력·작업 버퍼도 제외했다.

**tracemalloc은 추적되지 않는 네이티브 코덱 할당을 제외**하므로 완전한 메모리
계정이 아니다. 대신 준비 단계와 이동 단계를 나눠, 전체 상주가 준비에서 약
5.58MiB를 쓰고 이동 중에는 약 2.14MiB로 내려오는 것처럼 **언제** 메모리가
늘어나는지 보여준다. **RSS는 Python 인터프리터·NumPy·코덱 import를 포함한 프로세스
전체 high-water mark**이며 "기준" 값조차 현재 RSS가 아니라 이미 HWM이다. 한
프로세스 안에서 단조 증가하므로 비교군 간 차이를 캐시의 순 메모리로 해석할 수
없다. 실제로 8청크의 전체 HWM(38.516MiB)은 4청크(37.469MiB)보다 높았고, 걷기에서
전체 상주는 40.875MiB였다. **이 작은 입력에서 캐시가 항상 RSS를 줄였다고 주장하지
않는다.**

### 범위와 한계

- `macos_nocache`의 F_NOCACHE 요청은 **캐시를 비웠다고 검증한 물리적 콜드 읽기가
  아니다.** `warm_buffered`도 이 스크립트가 반복마다 한 번 OS 페이지 캐시를
  준비했다는 뜻일 뿐이며, 두 모드 모두 애플리케이션 캐시와는 다른 층이다.
- 120단계 합계는 **로더 시간의 합**이며 렌더링·물리·검증·보고서 기록을 포함한
  실제 120프레임 벽시계 시간이 아니다.
- HCIX 인덱스 자체에는 체크섬이 없다. 구조와 읽은 페이로드는 검증하지만 읽지
  않은 데이터의 손상은 탐지하지 않는다. 범위는 하이트맵 전용이며 엔진·메시·
  텍스처·GPU·충돌 준비는 포함하지 않는다.
- 단일 macOS 장치의 단일 실행이다. 동시 읽기, 네트워크 파일시스템, 다른 저장장치는
  검증하지 않았다.

4개, 비-Darwin 전용 1개). 환경: macOS 26.6.2 arm64, Python 3.13.9, NumPy 2.5.4,
zstandard 0.25.0, lz4 4.4.5.

- [실행 계약·리포트 형식](../docs/town-cache-method.md)

`town-cache-*-v2.json`은 크기가 커서 공백 없는 compact JSON이다. 프레임·반복 단위
원시 값은 정수 나노초(`*_ns`)이고 집계는 모두 밀리초 통계(`median_ms`/`p95_ms`/
`max_ms`)이므로, 집계 이름에는 `_ns`를 붙이지 않는다.

```sh
uv run python scripts/compare_town_cache.py --schedule benchmarks/town-movement-1024-v1.json --repeats 3 --cache-sizes 4,8 --memory-repeats 3 --output benchmarks/my-town-cache.json --containers-dir data/terrain-local/my-town-cache
uv run python scripts/compare_town_cache.py --schedule benchmarks/town-movement-1024-seed2-v1.json --repeats 3 --cache-sizes 4,8 --memory-repeats 3 --output benchmarks/my-town-cache-seed2.json --containers-dir data/terrain-local/my-town-cache-seed2
PYTHONPATH=. uv run python benchmarks/audit_town_cache_final.py
```

기본값은 `--repeats 3`, `--cache-sizes 4,8`, `--memory-repeats 3`이며, 청크 변과
시야는 스케줄에 기록된 값(위 측정은 256·256)을 쓴다. 메모리 사이드카 경로는
`--output`의 확장자를 바꾼 것이며 이름 뒤에 덧붙이지 않는다. 즉
`my-town-cache.json`의 사이드카는 `my-town-cache.memory.json`이다. `--output`,
사이드카, `--containers-dir`은 모두 기존 경로를 덮어쓰지 않으므로 재실행 시 새
경로를 지정해야 한다. 위 최종 산출물과 컨테이너는 그대로 보존해야 하며, 감사
스크립트는 그 두 리포트를 읽고 최종 evidence JSON만 다시 쓴다.

### 초안 단계 기록 (역사)

`town-cache-1024-v1.json`·`town-cache-1024-seed2-v1.json`과 그 시작 관측·메모리
감사, [초안 감사 보고서](town-cache-audit.md), [초안 CLI 사본](reference/compare_town_cache_draft_v1.py),
[초안 감사 스크립트](audit_town_cache.py)는 **감사 미승인 초안 CLI** 단계의
역사적 기록이다. 그 단계에서는 소스 해시 검증이 일부 파일을 건너뛰었고, 원시 시작
시간이 저장되지 않아 감사자가 별도 관측으로 보완했으며, 집계 이름의 단위가 실제
단위와 달랐고 메모리 CLI도 없었다. 위 v2 결과가 이 초안을 **대체**한다. 라이브러리
구현(`horizon/town_cache.py`)과 측정 수치 자체는 당시에도 독립 검산을 통과했으므로
초안 리포트는 삭제하지 않고 비교용으로 남겨 둔다.
