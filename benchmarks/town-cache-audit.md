# 청크 재사용 캐시와 전체 맵 상주 감사

README와 기존 마을·청크·이동 기준선을 정리한 커밋 `bfe546f`를 `DoTaeIn/Horizon`의 `origin/main`에 푸시했다. 이후 캐시 실험은 로컬 변경이며 아직 커밋·푸시하지 않았다.

## 구현과 완료 범위

- Claude Opus가 `horizon/town_cache.py`의 `ChunkRegionCache`와 `WholeMapResident`를 구현했고, Claude Sonnet이 독립 테스트와 비교 CLI 초안을 작성했다. Codex는 파일 범위 감사, 수정 요청, 실행, 독립 검산 및 감사 기록만 담당했다. 이 문서와 `audit_town_cache*.py`는 독립 감사 코드다.
- 청크 캐시는 시작할 때 헤더·전체 인덱스를 한 번 읽고 열린 비버퍼링 파일 핸들을 유지한다. 겹치는 디코딩 배열은 재사용하며 누락된 청크만 읽고 푼다. 캐시 배열 수는 지정 용량 이하로 유지한다.
- 요청 시작 때 이미 캐시에 있는 필요 청크를 먼저 합성하고 MRU로 갱신한 뒤, 나머지 청크를 행 우선 순서로 읽어 LRU를 교체한다. 한 요청 안에서 아직 필요한 기존 청크를 먼저 버리는 재읽기를 제거했다. 캐시보다 큰 ROI도 정확히 합성한다.
- 전체 상주는 시작 때 전체 파일을 한 번 읽고 검증·압축 해제해 배열을 보관한다. 이후 요청은 같은 크기의 소유 배열로 잘라 복사하며 파일을 읽지 않는다.
- 두 캐시 API는 원본과 공유하지 않는 ROI를 반환한다. 청크 캐시는 매 요청 fstat으로 파일의 크기·mtime·ctime 변화를 검사하며 변경·읽기·검증 실패 시 닫고 상태를 비운다. 호출자에게 반환한 배열을 변경해도 캐시에 영향을 주지 않는다.
- 최종 자동 테스트 350개 중 345개 통과·5개 환경별 건너뛰기. 별도 무작위 감사로 513×769, 세 코덱, 캐시 용량 1·4·8에서 2,700회 결과와 1,350번 LRU 전이를 독립 검산했다.

## 측정 방법

- 기존 `town-movement-1024-v1.json`과 `town-movement-1024-seed2-v1.json`에 저장된 좌표를 그대로 재생했다. 새 이동 경로를 생성하지 않았다. 1024×1024 uint16, 256청크·256×256 시야, 경로별 120단계×3회, 3코덱×2 I/O 모드×4비교군×2시드 = 총 51,840회 로딩.
- 매 경로 반복마다 새 세션을 만들었다. LRU는 비어 있는 상태, 전체 상주는 새로 전체를 읽고 푼 상태로 시작한다. 준비 시간, 첫 시야까지의 시간, 이동 시간, 준비를 포함한 120단계 로더 합계를 구분했다.
- warm 모드는 세션 생성 전에 양쪽 파일을 한 번씩 읽어 OS 캐시를 준비했다. F_NOCACHE 요청 모드는 별도 준비를 하지 않았다. 물리 SSD cold read를 검증한 실험이 아니다.
- 요청마다 비교군 실행 순서를 회전했다. 요청 결과의 dtype과 바이트 일치는 타이머 밖에서 검증했다. 로더의 total_ns는 캐시 조회·LRU 갱신·출력 할당·읽기·검증·복원을 포함한 핵심 경로의 실제 경과 시간이다. read_ns 외의 모든 비용은 decode_ns에 포함하므로 이 이름에는 복원 외의 합성·캐시 관리도 포함된다.
- CLI 초안이 원시 시작 시간들을 저장하지 않아, Codex는 원래 생성자를 그대로 호출하는 관찰 래퍼로 반환된 startup_metrics를 타이머 뒤에서 별도 기록했다. 로딩 메서드는 변경하지 않았다. 각 보고서의 시작 관측 162개, 합계 324개를 독립 검산에 사용했다.
- 메모리는 시간 측정과 분리했다. 기존 Claude 로더 한 개만 새 Python 프로세스에 만들어 같은 경로를 재생하는 독립 감사 216개(2시드×3코덱×3경로×4비교군×3회)를 실행했다. 자식 프로세스에는 원본 전체 맵·이전 대형 보고서·다른 비교군을 넣지 않았다. 출력 배열은 매 단계 하나만 보유하고 해시 후 해제했다. 모든 출력의 연속 SHA-256을 부모의 원본 크롭 해시와 비교했다.

## 요청당 지연

시드 20261012, delta+Zstd, warm_buffered, ms. 360개 요청의 중앙값 / p95이다. 초기 준비는 아래에 별도로 기록했다.

| 방식 | 걷기 | 경계 왕복 | 순간이동 | 최대 보관 값 배열 |
|---|---:|---:|---:|---:|
| stateless | 0.9692 / 1.1570 | 1.0412 / 1.1645 | 0.9817 / 1.2430 | 0.00 MiB |
| lru4 | 0.0089 / 0.3312 | 0.5042 / 0.5710 | 0.5339 / 1.0535 | 0.50 MiB |
| lru8 | 0.0085 / 0.2804 | 0.0088 / 0.0184 | 0.2932 / 0.9618 | 1.00 MiB |
| whole_resident | 0.0044 / 0.0115 | 0.0040 / 0.0088 | 0.0100 / 0.0133 | 2.00 MiB |

전체 맵 상주는 이동 중 요청 지연이 가장 짧다. 8청크 캐시는 걷기·경계 왕복에서 대부분 적중하지만 순간이동에서는 누락 청크를 읽어야 하므로 비용이 커진다. 이 작은 2MiB 맵에서는 전체 상주가 충분히 현실적인 기준선이다.

4청크 캐시의 경계 왕복 최대 요청은 시드별 32.971ms·37.413ms였다(p95는 0.571ms·0.602ms). 원인 귀속은 검증하지 않았고 표본을 제거하지 않았다. 낮은 중앙값이 게임 프레임 지연 보장을 뜻하지 않는다.

| 이동 | 4청크 적중률 | 8청크 적중률 | 8청크 실제 보관 피크 |
|---|---:|---:|---:|
| 걷기 | 95.57% | 95.84% | 1.00 MiB |
| 경계 왕복 | 49.58% | 98.75% | 0.75 MiB |
| 순간이동 | 21.41% | 52.39% | 1.00 MiB |

적중률에는 비어 있던 캐시의 첫 요청도 포함된다. 경계 왕복은 필요한 여섯 청크를 8청크 캐시에 담고 나면 모두 적중한다. 4청크 용량은 여섯 청크 전체를 담지 못하므로 계속 두 청크씩 교체한다.

## 초기 비용과 120단계 합계

시드 20261012, delta+Zstd, warm_buffered. 합계는 각 반복의 준비+120개 로더 시간 합을 구한 뒤의 중앙값이다. 렌더링·물리·검증·보고서 기록을 포함한 실제 120프레임 벽시계 시간이 아니다.

| 이동 | 방식 | 첫 시야까지 ms | 준비+120단계 ms |
|---|---|---:|---:|
| 걷기 | stateless | 1.103 | 92.869 |
| 걷기 | lru4 | 1.047 | 5.291 |
| 걷기 | lru8 | 1.032 | 4.990 |
| 걷기 | whole_resident | 4.802 | 5.441 |
| 경계 왕복 | stateless | 1.061 | 125.849 |
| 경계 왕복 | lru4 | 1.029 | 61.550 |
| 경계 왕복 | lru8 | 1.044 | 2.768 |
| 경계 왕복 | whole_resident | 4.406 | 5.046 |
| 순간이동 | stateless | 0.553 | 99.594 |
| 순간이동 | lru4 | 0.571 | 72.877 |
| 순간이동 | lru8 | 0.575 | 44.704 |
| 순간이동 | whole_resident | 4.279 | 5.488 |

첫 시야는 LRU가 약 0.57~1.05ms, 전체 상주가 약 4.28~4.80ms다. 전체 상주는 초기에 전체를 푸는 비용을 한 번 내고 이후 요청이 빠르다. 120단계 합계에서는 8청크 캐시가 경계 왕복에서 약 2.77ms, 전체 상주가 약 5.05ms였지만 순간이동에서는 약 44.70ms 대 5.49ms로 전체 상주가 크게 앞섰다. 걷기는 약 4.99ms 대 5.44ms로 비슷한 크기이며 작은 차이를 일반화하지 않는다.

두 번째 시드도 같은 방향이었다. delta+Zstd warm의 8청크 요청 중앙값은 걷기 0.0085ms·경계 왕복 0.0106ms·순간이동 0.4858ms, 전체 상주는 0.0051·0.0066·0.0110ms였다. 두 시드·모든 코덱·F_NOCACHE 요청 모드의 세부 수치는 evidence와 원시 보고서에 있다.

## 메모리

정확한 값 배열 크기와 추적 가능한 할당, 프로세스 전체 RSS를 구분한다. 반환되는 256×256 출력 배열 하나는 각 방식 모두 0.125MiB이며 보관 배열 열에서는 제외한다. 인덱스·Python 객체·압축 입력·작업 버퍼도 보관 배열 크기에서는 제외한다. 이 비용은 tracemalloc 또는 프로세스 RSS 피크에 일부/전체 반영된다.

시드 20261012, delta+Zstd, 걷기 경로, 독립 프로세스 3회 중앙값. 단위 MiB.

| 방식 | 최대 보관 값 배열 | 준비+이동 추적 할당 피크 | 이동 중 추적 할당 피크 | 프로세스 RSS 피크 | RSS 기준 HWM |
|---|---:|---:|---:|---:|---:|
| stateless | 0.000 | 0.629 | 0.629 | 37.281 | 35.156 |
| lru4 | 0.500 | 0.943 | 0.943 | 37.234 | 35.594 |
| lru8 | 1.000 | 1.444 | 1.444 | 36.469 | 35.219 |
| whole_resident | 2.000 | 5.578 | 2.136 | 40.672 | 35.406 |

8청크 캐시는 보관 배열의 상한을 전체 상주의 절반으로 줄이고, 이 delta+Zstd 걷기 경로에서 추적 가능한 준비+이동 피크는 약 1.44MiB 대 5.58MiB였다. 전체 상주가 준비를 마친 후에는 추적 가능한 이동 피크가 약 2.14MiB로 내려간다.

tracemalloc은 추적되지 않는 코덱 네이티브 할당을 제외한다. RSS는 Python·NumPy·코덱 import와 런타임을 포함한 프로세스 전체 high-water mark다. 기준 HWM도 현재 RSS가 아니므로 차이를 캐시의 순 메모리라고 해석하지 않는다. 예를 들어 순간이동의 8청크 RSS 중앙값은 약 42.41MiB로 전체 상주 약 41.02MiB보다 높았다. 이 작은 입력에서 RSS가 항상 줄었다고 주장하지 않는다.

## 감사에서 수정하거나 남긴 부분

- 최초 캐시 초안은 선택된 구간 시간만 합산해 LRU 조회·출력 할당 등 비용을 빠뜨렸다. 실제 핵심 경로의 경과 시간으로 수정한 뒤 측정했다.
- 순차 행 우선 처리에서 새 청크를 넣다가 이번 요청에 필요한 기존 청크를 먼저 밀어내는 문제가 있었다. 기존 필요 청크를 먼저 합성·갱신하는 두 단계로 고쳤고 회귀 테스트를 추가했다.
- 비교 도구 담당의 내부 백그라운드 작업이 범위를 넘어 Opus 소유 로더를 작성해 충돌했다. 해당 작업을 중지하고 Opus 세션에서 자체 구현을 복원·수정했다. 최종 라이브러리와 모든 코드 해시를 다시 확인했다.
- Claude CLI가 세션 한도에 도달해 범용 메모리 CLI와 문서, 비교 CLI의 마지막 정리가 완료되지 않았다. 기능 코드는 Claude가 작성한 것을 유지했고 Codex가 대신 완성하지 않았다. 메모리 수치는 별도의 독립 감사이며 미완성 CLI를 성공했다고 보고하지 않는다.
- `scripts/compare_town_cache.py`는 **감사 미승인 초안**이다. 기본 memory-repeats=3은 아직 없는 `scripts/measure_town_cache_memory.py`를 호출하므로 현재 실행에는 `--memory-repeats 0`이 필요하다. 생성자 실패 시 명시적인 세션 정리, 누락된 소스 해시 거부, 지원하지 않는 명시 모드 거부, 출력 shape 검사, 원시 startup 기록, 시간 단위 이름도 다음 Claude 작업에서 정리해야 한다. 현재 정상 경로의 두 보고서는 독립 검산으로 보완해 수치가 일치함을 확인했다.
- 두 원시 시간 보고서의 51,840개 요청에 대해 경로 ROI·회전 순서·정확한 청크 선택·두 단계 LRU 전이·읽기 바이트/호출 수·보관 배열 크기를 검산했다. 관측한 원시 준비 시간을 붙여 first-viewport와 준비 포함 합계를 다시 계산했다. 입력·컨테이너·실행 소스·이전 스케줄 파일 해시와 모든 시간 합계·중앙값·p95·최대도 확인했다.
- 기존 실험용 HCIX에는 인덱스 자체 체크섬이 없다. 구조와 읽은 페이로드는 검증하지만 읽지 않은 데이터의 손상은 탐지하지 않는다. 이 실험은 높이맵 로더이며 게임 엔진·메시·텍스처·GPU·충돌 준비의 성능 측정이 아니다.
