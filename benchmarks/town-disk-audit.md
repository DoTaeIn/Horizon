# 256 청크 디스크 읽기·복원 비교 감사

측정일: 2026-10-12. Claude Opus가 `horizon/town_disk.py`, Sonnet 작업 두 개가 모듈 테스트와 CLI·문서·CLI 테스트를 구현했다. Codex는 검토와 수정 요청, 최종 측정, 독립 검증 및 이 감사 기록을 담당했다. 기존 높이맵 생성기와 코덱은 변경하지 않았다.

## 비교 대상과 측정 조건

이전과 같은 독창적인 합성 마을·도로 높이맵 두 개를 사용했다. 각각 1024×1024 little-endian uint16, 원본 2 MiB이며 시드는 20261012와 20261013이다. 실제 게임 에셋은 포함하지 않는다. 청크는 256×256, 맵당 16개다. 단일 컨테이너와 인덱스 포함 청크 컨테이너를 실제 파일로 저장했다.

세 코덱(Zstd, LZ4, 행 차분+Zstd), 두 읽기 조건, 두 작업(전체/부분), 두 저장 방식(단일/청크)을 비교했다. 각 조합은 워밍업 2회 후 50회 실행했다. 두 맵 합계 **2,400회 로딩 표본**이며, 모든 결과를 시간 측정 밖에서 원본과 shape·dtype·바이트 단위로 비교했다.

- **전체 로딩:** 단일 파일 전체 읽기·복원 vs 청크 파일의 전체 인덱스·페이로드 읽기와 모든 청크 재구성.
- **부분 로딩:** 단일 파일 전체 읽기·복원 후 해당 영역의 소유 배열 복사 vs 헤더·인덱스 항목 하나·압축 청크 하나만 읽기·복원. 두 방식은 같은 256×256 값을 반환한다.
- 매 호출은 파일을 새로 열고, 필요시 캐시 플래그를 요청하고, fstat·seek·read·close한 다음 복원한다. 파일 핸들이나 파싱한 인덱스를 재사용하지 않는다.
- Python 파일 버퍼는 `buffering=0`이다. 전체 단일 파일은 헤더/페이로드 2회 읽기, 전체 청크 파일은 헤더/인덱스/연속 페이로드 3회 읽기, 부분 청크는 헤더/선택 항목/선택 페이로드 3회 읽기를 수행한다. 짧은 읽기는 정확한 길이를 채울 때까지 재시도하며 개별 호출을 센다.
- `read_ns`에는 열기·캐시 플래그·fstat·seek·인덱스 검증·읽기·닫기를 포함한다. `decode_ns`에는 디코드·코덱 체크섬·전체 재구성 또는 영역 복사를 포함한다. `total_ns = read_ns + decode_ns`다. 전체 파일 해시 계산은 측정 밖이다.
- 요청 좌표는 `[0,1024)` 픽셀을 균등하게 뽑고 해당 청크로 매핑했다. 코덱과 읽기 조건 모두 같은 50회 일정을 사용한다. 매 반복의 단일/청크 실행 순서는 교대한다. 코덱과 읽기 조건의 바깥 루프 순서는 고정이며 이 한계를 JSON에 기록했다.

### 캐시 조건의 의미

`warm_buffered`는 매 측정 직전에 **양쪽 파일을 모두** 일반 읽기로 캐시에 준비한다. 이 준비 시간은 측정하지 않는다.

`macos_nocache`는 캐시 준비를 추가하지 않고 새 파일 디스크립터에 `fcntl(fd, F_NOCACHE, 1)`을 실제 호출한다. 플래그를 사용할 수 없거나 호출이 실패하면 실패하며 일반 읽기로 바꾸지 않는다. 로컬 SDK에서 상수 48을 확인했고, Codex는 실제 시스템 호출을 대체하지 않는 래퍼로 네 로딩 경로의 호출을 확인했다.

**F_NOCACHE 요청은 이미 존재하는 캐시 페이지를 제거했다는 증거가 아니며, SSD·컨트롤러 캐시까지 비운 물리적 콜드 읽기가 아니다.** 파일 작성·사전 검증·앞선 측정으로 페이지가 남아 있을 수 있다. 두 조건 사이의 작은 차이로 캐시 비활성화의 속도 이득을 주장하지 않는다. `bytes_read`는 애플리케이션이 읽은 데이터 길이이며 물리적 SSD 전송량이나 파일시스템의 내부 읽기 증폭을 측정한 값이 아니다. 플래그의 의미는 [Apple fcntl 문서](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html), 상수는 [Apple XNU 헤더](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/fcntl.h)를 참고한다.

## 기본 맵 결과

차분+Zstd, 단일 파일 375,841바이트, 청크 파일 376,285바이트(+0.118%). 시간은 **중앙값 / p95, ms**이며 파일 열기부터 복원 완료까지다.

| 작업 | 캐시 준비 일반 읽기 | F_NOCACHE 요청 |
| --- | ---: | ---: |
| 단일 파일 전체 로딩 | 4.184 / 4.354 | 4.225 / 4.656 |
| 청크 파일 전체 로딩 | 4.239 / 4.684 | 4.271 / 5.044 |
| 단일 파일 전체 읽기·복원 후 영역 복사 | 4.205 / 4.488 | 4.243 / 4.489 |
| 선택한 청크만 읽기·복원 | 0.286 / 0.342 | 0.273 / 0.359 |

캐시 준비 조건의 부분 로딩은 중앙값 기준 **약 14.7배** 빠르다. 전체 로딩은 청크 방식이 중앙값 기준 약 1.3% 느렸으며, 속도 이득을 확인하지 못했다. 두 방식의 출력 작업량이 같은 것은 각 작업 안의 쌍이다. 전체 맵 로딩과 한 청크 로딩을 같은 작업량으로 비교해서는 안 된다.

부분 청크의 애플리케이션 읽기량은 인덱스 포함 **20,351~25,393바이트**, 중앙값 23,631바이트다. 단일 방식은 매번 375,841바이트를 읽는다. 중앙값 기준 읽기량은 약 93.7% 적다. 캐시 준비 조건에서 부분 청크의 읽기 단계 중앙값은 0.018ms, 복원 단계는 0.267ms다. 각각의 중앙값을 더한 값이 전체 중앙값과 정확히 같아야 하는 것은 아니다.

### 다른 시드 확인

다른 시드의 차분+Zstd 결과에서 캐시 준비 조건은 전체 단일 4.565ms, 청크 전체 4.747ms, 전체 읽기 후 영역 복사 4.573ms, 부분 청크 0.337ms였다. 부분 로딩은 약 13.6배 빠르고, 전체 로딩의 이득은 없었다. F_NOCACHE 요청 조건의 같은 값은 4.593 / 4.693 / 4.609 / 0.314ms다.

### 다른 코덱 확인

기본 맵, 캐시 준비 조건의 중앙값이다. 부분 로딩의 두 열은 동일 영역을 반환한다.

| 코덱 | 단일 / 청크 파일 KiB | 단일 전체 ms | 청크 전체 ms | 단일 읽기 후 영역 ms | 부분 청크 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Zstd | 486.47 / 481.95 | 2.493 | 2.589 | 2.493 | 0.210 |
| LZ4 | 799.52 / 801.95 | 1.644 | 1.734 | 1.654 | 0.124 |
| 차분+Zstd | 367.03 / 367.47 | 4.184 | 4.239 | 4.205 | 0.286 |

차분+Zstd는 저장 공간에 유리하고 LZ4는 이 입력의 로딩 지연에 유리하다. 어느 코덱이 최적인지는 저장·메모리·지연 예산에 달려 있다.

## 독립 감사와 수정

- 두 입력을 재생성해 이전 메모리 실험과 입력 해시가 같은지 확인했다.
- 최종 JSON의 소스 해시와 실제 소스, 컨테이너의 측정 전후 해시와 실제 파일을 대조했다.
- 2,400회 표본의 시간 합계, 각 중앙값·p95와 표본 수를 재계산했다.
- 각 부분 요청에 대해 실제 파일의 선택 인덱스 항목을 파싱해 `bytes_read = 24 + 32 + 선택 컨테이너 길이`임을 확인했다. 전체 작업의 읽기량은 파일 크기와 같았다. 모든 코덱·조건의 요청 일정도 같았다.
- 실제 F_NOCACHE 호출을 확인했고, 시스템 호출을 흉내 낸 측정값을 사용하지 않았다.
- 초기 구현의 파일 크기 거부 시 핸들 누수, 컨테이너 준비 실패 시 부분 파일 잔류를 찾아 수정하도록 했다.
- 초기 CLI의 임의 Beta 좌표 분포와 마지막 픽셀 누락을 반려하고 균등 픽셀 좌표로 수정하도록 했다.
- 초기 CLI의 기존 빈 디렉터리 삭제를 독립 재현하고, 소유권 추적과 보존 회귀 테스트로 수정하도록 했다. 실패 주입 테스트의 잘못된 패치 대상도 수정했다.
- 최종 전체 테스트: **244개, 239개 통과·5개 건너뛰기·실패 0**. Windows 전용 4개와 비-Darwin 전용 1개가 이 Mac에서 건너뛰어진 항목이다.

## 적용 범위와 다음 단계

이 결과는 단일 Mac의 일반 데스크톱 환경과 합성 맵 두 개에 한정한다. 하드웨어 격리나 완전한 콜드 부팅을 검증하지 않았다. 엔진·GPU·충돌 준비와 메모리 피크는 측정하지 않았다.

HCIX는 여전히 실험용 형식이다. 전체 읽기는 인덱스의 격자·범위·연속성·커버리지를 검사하고, 부분 읽기는 요청한 항목과 컨테이너만 검사한다. 읽지 않은 인덱스나 다른 청크의 손상까지 검출한다고 주장하지 않는다. 각 청크의 데이터는 기존 코덱 체크섬으로 검사한다.

현재 부분 API는 **격자에 맞는 청크 하나**를 반환한다. 임의의 256×256 창이 청크 경계를 가로지르는 경우나 여러 청크 요청, 연속 이동·인덱스 재사용·캐시 재사용은 별도 실험이다. 다음 구현은 임의 영역에 필요한 청크 집합을 읽고 합성하는 경로와 실제 이동 패턴 비교가 적절하다.
